# 振り返り

## 1. この文書について

しおや農園（小規模な家族農家の直販ECサイト）の開発を振り返り、進め方の判断と、次のプロジェクトに持ち越すことをまとめた文書です。

- 対象の期間：企画・設計 2025-07-21〜、実装 2026-10-17〜2026-11-15（この文書の時点）
- 開発体制：開発者1人と Claude Code（Anthropic の AI コーディングツール）
- README との分担：README はアプリの概要・環境構築・実装の範囲を、この文書は「どう進めたか・何を学んだか」を扱います。

## 2. 進め方の全体像

実装は次の順に進めました。

1. 公開側の機能（商品・カート・購入・予約・サンクスメール・マイページ・パスワード再設定）のバックエンド
2. コード全体の横断確認と修正
3. 1回目の E2E テスト（PC のみ）
4. Figma のデザインに沿った公開側の画面
5. 2回目の E2E テスト（壊れたテストの修正と SP の追加）
6. 管理画面（全画面）
7. 後回しにしていた機能（管理者の二段階認証・資材管理・会員登録完了メール）と、見た目の細部
8. 3回目の E2E テスト（管理画面を追加）
9. 設計書と実装の差分確認と修正
10. 依存パッケージの更新

順番を決めた主な理由は2つです。

- **Figma を読み込む回数に上限があった。** Figma のデザインは MCP（Claude Code から Figma を読むための仕組み）で取得していましたが、無料プランの呼び出し上限に途中で達しました。リセットまでの約12日間は、画面を仮の Blade にしてバックエンドだけを先に進め、リセット後に画面をまとめて仕上げました。
- **画面を作り込む前に E2E を用意した。** 画面の実装でバックエンドの動きを壊していないかを確かめるため、先に PC の E2E を作り、安全網にしました。見た目に左右されにくいよう、要素はロール（ボタン・見出しなど）とラベルで取得しています。

## 3. Claude Code との開発体制

### 3.1 役割分担

| 担当 | 役割 |
|---|---|
| 開発者（私） | 仕様と方針の決定、受け入れの判断 |
| Claude Code のメインセッション | 作業の段取り、サブエージェントへの依頼文の作成、結果の確認、報告 |
| `implementer` エージェント | 実装とテストの作成 |
| `uat-tester` エージェント | Playwright で画面を操作して受け入れテスト（UAT）を行い、結果を記録 |
| `/code-review` | 差分のレビュー |
| `doc-diff-checker` エージェント | 設計書と実装のずれを、事実だけ一覧にする（読み取り専用） |

1つの機能は、作業ブランチを切る → 受け入れ条件と UAT のシナリオを作って私が確認する → 実装・テスト → UAT → レビュー → 私がチェックリストで受け入れる、という流れで進めました。この流れは `/add-feature` スキル（[.claude/skills/add-feature](../.claude/skills/add-feature/SKILL.md)）にしてあります。

最初は、レビュー後の小さな修正をメインセッションが直接直していました。途中から、小さな修正でも `implementer` に任せ、メインセッションは確認と報告に専念する形に変えました。直した本人が確認もすると見落としやすく、役割を分けたほうが確認の目が保てるためです。

### 3.2 依頼文ではなく仕組みで守る

サブエージェントへの依頼文で git の操作を禁止していたのに、`implementer` が `git mv` や `git reset` を実行したことがありました。別の作業では、依頼文に「実行できなければ報告」と書いたため、許可の確認が必要なコマンドを「できたので実行した」こともありました。

ここから、**依頼文は「お願い」であって保証にはならない**と考え、次の2つで守るようにしました。

- **依頼文の書き方**：許可が要る操作は「実行しない。必要なら止めて報告」と書く。「できなければ報告」のように、できるなら実行してよいと読める書き方はしない。
- **hook（ツールの実行前に走る検査）で止める**：

| hook | 止めるもの |
|---|---|
| [guard-agent-commands.py](../.claude/hooks/guard-agent-commands.py) | サブエージェントによる git の書き込み・削除・DB やコンテナの破壊など（メインセッションは対象外） |
| [guard-main-branch.py](../.claude/hooks/guard-main-branch.py) | `main` ブランチ上でのアプリのコードの編集 |
| [guard-migrations.py](../.claude/hooks/guard-migrations.py) | コミット済み・適用済みのマイグレーションの書き換え |
| [guard-merge.py](../.claude/hooks/guard-merge.py) | マージ前の検証を通っていないブランチの `main` へのマージ |

`doc-diff-checker` も同じ考え方で、使えるツールを読み取り（Read・Grep・Glob）だけに絞り、編集できないようにしています。

### 3.3 検証の層

| 層 | 確かめること | 規模（この文書の時点） |
|---|---|---|
| PHPUnit | クラス・機能単位の動き | 2073件、カバレッジ 98.8% |
| Larastan（レベル5） | 型の誤りなど | エラー0件 |
| UAT | 機能ごとの受け入れ条件を、実際の画面で確かめる | シナリオ 32ファイル |
| E2E（Playwright） | 利用者の一連の流れを、繰り返し確かめる | 会員側14項目・管理画面11項目を PC と SP で（Stripe Checkout の2件は別に実行） |
| マージ前の検証（[scripts/verify.sh](../scripts/verify.sh)） | CI と同じ項目に、ルートと Blade のキャッシュの作成を加えたもの | マージのたびに実行 |
| CI（GitHub Actions） | `main` への push ごとに、上の項目（E2E 以外）を実行 | |

マージ前の検証は、CI で依存パッケージの脆弱性チェックが失敗したのをきっかけに足しました。CI で落ちてから気づくのでは遅いので、マージの前に同じ項目を手元で通し、通ったコミット以外はマージできないよう hook で止めています。

## 4. うまくいったこと

- **設計書は md を正とした。** 実装中に設計書と違う判断をしたときは、その機能のブランチの中で設計書も直しました。草案の Excel は更新せず、md だけを実装に合わせることで、正がどれかで迷わずに済みました。
- **Figma の上限に合わせて進め方を変えた。** SP のデザインは Figma で作らず、PC の値をもとに SP の方針を文章で決め、実装後に幅 414px の画面のスクリーンショットで確かめました。Figma から値を取るのは画面のまとまりごとに1回にし、取った値はすべて依頼文に書いて、何度も読みに行かないようにしました。
- **途中と最後に、全体を確認した。** 公開側の機能が揃った時点でコード全体を横断して確認し、重複や規約からのずれを18件直しました。全機能の実装後には、`doc-diff-checker` に設計書ごとに実装と照らし合わせてもらいました。経緯を知らないエージェントに見てもらうことで、「意図した変更だから」と見過ごしていたずれも洗い出せました。
- **見た目の細部は、最後にまとめて直した。** 機能の実装中に気づいた細かい見た目の問題は記録だけしておき、全機能の実装後にまとめて直しました。機能の実装の流れを止めずに済み、同じ部品の修正を1回で済ませられました。

## 5. うまくいかなかったこと・次に変えること

- **実装中に決めたことが、デザインに反映されていなかった。** 公開側の画面を作る途中で、ボタンの文字色・読みにくい文字色の調整・モーダルの閉じ方などを決めましたが、Figma の管理画面のデザインには入っていませんでした。管理画面の実装では、Figma の値と実装済みの判断を毎回照らし合わせる必要がありました。次は、デザインと違う判断をしたら、その場で一覧に残すか Figma に反映します。
- **レビューが汎用の `/code-review` だけだった。** 一般的な不具合は見つかりましたが、プロジェクトの規約や設計書を前提にした指摘は出ません。次は、規約（`.claude/rules`）と設計書を読んだうえでレビューする、専用のレビュアーのエージェントを流れに入れます。
- **手元では通るテストが、CI だけで落ちた。** 環境変数を書き換えるテストで、Laravel の `env()` は `$_SERVER` を先に読みます。CI では設定の雛形ファイルの値が `$_SERVER` に入っていて、書き換えが効いていませんでした。手元の設定ファイルにはその行がなかったため、気づけませんでした。環境変数を書き換えるテストでは、`$_SERVER`・`$_ENV`・`putenv` の3つを揃えるようにしました。
- **依存パッケージの更新で、意図しないメジャー更新が混ざった。** `composer update` を素で実行すると、Symfony の一部のパッケージだけが 8 系に上がりました。今回は対象のパッケージを 7.4 系に留める指定を付けて実行し直しました。更新のときは、テストを流す前に、ロックファイルの差分でメジャー更新が混ざっていないかを確かめます。
- **素材の規約の確認が、公開の後になった。** 写真とアイコンはフリー素材を使っていて、「商用利用可」までは確認していました。しかし、どの配布元も**素材の再配布**を禁止しており、リポジトリに画像ファイルを入れて公開すると、それに当たるおそれがありました。リポジトリを一時的に非公開にし、画像を管理対象から外して全履歴からも消してから、公開に戻しました。
  - さらにその作業の途中で、画像を管理対象から外したブランチをマージしたときに、手元の画像ファイルまで消えてしまいました（まだ管理対象だったブランチに切り替えてからマージしたため）。作業前に取ったバックアップから戻せました。
  - 次は、素材を追加するときに規約（商用利用・再配布・クレジット表記）を確かめ、出どころを記録します。履歴の書き換えのような元に戻せない作業の前には、必ずバックアップを取ります。

## 6. 次のプロジェクトへの持ち出し

このプロジェクトで作ったルール・スキル・エージェント・hook と、作業中に Claude Code に残したメモを棚卸しし、次のように分けました（移す作業はこれから行います）。

| 分類 | 中身 | 分けた理由 |
|---|---|---|
| どのプロジェクトでも使う共通設定 | 日本語でやり取りする、修正もサブエージェントに任せる、許可が要る操作は依頼文で「実行しない」と書く、設計書は md を正とする、など | 毎回読み込まれるので、どのプロジェクトにも当てはまることだけを置く |
| 技術ごとの自作スキル（Laravel・Livewire・Figma） | Laravel のレイヤー構成・テスト・マイグレーションの書き換えの範囲、Livewire 同梱の Alpine の使い方、Figma の上限への対処と SP の作り方 | スキルは関係する作業のときだけ読み込まれる。Figma や Livewire は毎回使うとは限らないので、共通設定に入れずに分ける |
| テンプレート用のリポジトリ | `/add-feature`、エージェント3体、hook 4本、`verify.sh`、CI、E2E の実行の仕組み、`CLAUDE.md` の雛形 | パスやコンテナ名を設定にして、新しいプロジェクトに写して使う |
| この文書 | 判断の理由と学んだこと | ルールだけを写すと「なぜそうするか」が抜けるため |
