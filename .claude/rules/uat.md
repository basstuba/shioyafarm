# UAT（受け入れテスト）の規約

UATは、実装した機能が設計書とユーザーの要求どおりに動くかを、実際のブラウザで確かめるテスト。PHPUnitのテストとは別に行う。

- **シナリオ作成**：実装の前に、メインセッションが設計書から作り、ユーザーのOKをもらう。実装したコードを見て作らない。
- **実施**：PHPUnitが全件通った後に、`uat-tester` エージェントが Playwright MCP で http://localhost を操作して確認する。
- **受け入れ**：最後にユーザーがチェックリストで確認し、合否を決める。Claudeが受け入れを判断しない。

## ファイル

- 機能ごとに `docs/uat/<機能名の英語ケバブケース>.md`（例：`docs/uat/item-index.md`）を作る。ファイル名はブランチ名の `feat/` 以降に合わせる。
- スクリーンショットは `docs/uat/screenshots/<機能名>/<シナリオID>-<pc|sp>.png` に置く。主要な画面はシナリオごとにPC・SPを1枚ずつ、NGになったものは必ず残す。

## 画面幅

- PC：1280×800
- SP：414×896

管理画面は高齢の生産者が使うため、SPでは文字が小さすぎないか、ボタンが押しやすい大きさか（目安：高さ44px以上）、横スクロールが出ていないかも確認する。

## テストデータ

開発用のDBをそのまま使い、原則として作り直さない（手で登録したデータを消さないため）。

- 実施前に `docker compose exec php php artisan migrate` を実行し、未適用のマイグレーションだけを反映する。既存のマイグレーションは書き換えない規約（`.claude/rules/backend.md`）なので、これでスキーマは最新になる。
- シナリオに必要なデータは、シナリオの「前提」に書き、`php artisan tinker` などでその都度追加する。追加したデータ（テーブル・件数・識別できる値）は結果の「追加したデータ」に書く。追加したデータは消さない。
- 既存のデータがシナリオの邪魔になる場合（例：0件のときの表示を確認したい）は、`migrate:fresh --seed` で作り直してよいかユーザーに確認し、了承を得てから実行する。了承が得られない場合は、そのシナリオを「未実施」にして理由を書く。

## ファイルの書式

```markdown
# UAT：<機能名>

| 項目 | 内容 |
|---|---|
| 対象ルート | GET /items（shop.items.index） |
| ブランチ | feat/item-index |
| 根拠 | docs/04-feature-list.md「商品一覧」、docs/07-basic-design.md |
| 実施日 | 2026-10-18 |

## 受け入れ条件

| ID | 条件 |
|---|---|
| AC-1 | 公開中の商品だけが一覧に表示される |

## シナリオ

| ID | 対応AC | 画面幅 | 前提 | 手順 | 期待結果 |
|---|---|---|---|---|---|
| S-1 | AC-1 | PC/SP | 公開・非公開の商品が1件ずつある | /items を開く | 公開中の商品だけが表示される |

## 実施結果

| ID | PC | SP | 備考 | スクリーンショット |
|---|---|---|---|---|
| S-1 | OK | NG | SPで価格が2行に折り返す | screenshots/item-index/S-1-sp.png |

- コンソールエラー：なし
- メール（Mailpit）：対象外
- 追加したデータ：items に2件（名前「UAT公開商品」「UAT非公開商品」）

## ユーザー確認チェックリスト

- [ ] SPで商品一覧を開き、写真と価格が見やすい
- [ ] …

## 判定

- 受け入れ：未 / 済（ユーザーが記入する）
- コメント：
```

## 書き方のルール

- 受け入れ条件は、利用者から見た振る舞いで書く（「Serviceが〜を返す」のような実装の話は書かない）。
- シナリオは、正常系だけでなく、バリデーションエラー・0件・未ログイン・境界値も含める。
- 金額（送料・代引手数料¥330・合計）が出る画面は、期待結果に具体的な金額を書く。
- ユーザー確認チェックリストには、Claudeでは判断しにくいこと（見た目の印象、文言のわかりやすさ、実機での操作感など）を中心に書く。
